Domains and Required Seed Data

1) Users/Auth
- Minimum users:
  - ADMIN: admin@example.com / Password: Password123!
  - MANAGER: manager@example.com / Password: Password123!
  - STAFF: staff@example.com / Password: Password123!
- Fields:
  - id (uuid), email (unique), password (bcrypt hash), firstName, lastName, role in ['ADMIN','MANAGER','STAFF','VIEWER'], isActive true
- Purpose:
  - Login via POST /auth/login
  - Permissions via GET /auth/permissions

2) Products
- 20–30 products across 3–5 categories and 3–5 suppliers.
- Fields:
  - id, sku (unique), name, description (nullable), category, supplier, price (>0), cost (>0), reorderLevel (>=0), isActive true, createdAt, updatedAt
- Purpose:
  - GET /api/products list & filtering
  - GET /api/products/:id
  - GET /api/products/sku/:sku
  - Create/update endpoints validation

3) Inventory Levels
- 1 InventoryLevel per seeded Product.
- Mix inventory states (in-stock, low-stock, out-of-stock).
- Fields:
  - productId (FK), currentQuantity (>=0), reservedQuantity (>=0), availableQuantity (>=0), reorderLevel (>=0), lastRestockDate (nullable), nextRestockDate (nullable), updatedAt
- Purpose:
  - GET /api/inventory, GET /api/inventory/product/:productId
  - POST /api/inventory/adjust scenarios

4) Orders
- 10–20 orders spanning statuses: PENDING, CONFIRMED, SHIPPED, DELIVERED, CANCELLED, RETURNED
- Each order has 1–5 items referencing seeded Products, consistent unitPrice with product price, subtotal computed.
- Fields:
  - id, orderNumber, customerId (optional), customerName, customerEmail (optional), customerPhone (optional)
  - items: productId, quantity (>0), unitPrice (>0), subtotal (>0)
  - status, totalAmount, shippingAddress, notes (nullable), createdAt, updatedAt, shippedAt (nullable), deliveredAt (nullable)
- Purpose:
  - GET /api/orders list with pagination and filters
  - GET /api/orders/:id
  - GET /api/orders/summary
  - PUT /api/orders/:id (status update)
  - Add/remove items flows

5) Purchase Orders (POs) and Goods Receipts
- 8–12 POs across statuses: DRAFT, SUBMITTED, CONFIRMED, PARTIALLY_RECEIVED, RECEIVED, CANCELLED
- Each PO has 1–5 items referencing seeded Products.
- Some POs have GoodsReceipts to demonstrate receiving logic.
- Fields:
  - PO: id, poNumber, supplierId, status, totalAmount, expectedDate, receivedDate (nullable), notes (nullable), createdAt, updatedAt
  - PO Item: productId, quantity (>0), unitPrice (>0), subtotal
  - GoodsReceipt: id, receiptNumber, purchaseOrderId, receivedDate, notes (nullable), createdAt
- Purpose:
  - GET /api/purchase-orders, GET /api/purchase-orders/:id
  - Create/update flows

6) Reports and Inventory Transactions
- Transactions generated by orders (SALE) and returns (RETURN), POs (PURCHASE) to provide meaningful aggregates by date ranges.
- Create a spread of transaction dates over last 30–90 days.
- Purpose:
  - GET /api/reports with date filters

7) Alerts (Optional but helpful)
- Create low stock alerts (StockAlert) for a subset of products.
- Fields: id, productId, currentQuantity, reorderLevel, isResolved false, createdAt
- Purpose:
  - Inventory alerts views if any.

Seeding Implementation Checklist
- Seed ordering: Users -> Products -> Inventory Levels -> POs -> Goods Receipts -> Orders -> Inventory Transactions -> Alerts
- Ensure referential integrity and consistency:
  - For each OrderItem, adjust InventoryLevel (reserved and/or current/available) accordingly if simulating lifecycle.
  - For each PO receipt, update InventoryLevel current/available.
  - Maintain totals: order.totalAmount = sum(items.subtotal); PO totals likewise.
- Hash passwords with bcrypt (salt rounds 10+).
- Use deterministic SKUs (e.g., PROD-0001) and PO/Order numbers (e.g., ORD-*, PO-*).
- Distribute timestamps to enable reports and date filters.
